Installation

Install the recorder for VS Code for JetBrains for Neovim.

Setup takes a few minutes. You only do it once per computer.

You will need

  • Visual Studio Code 1.100 or newer. Check under Code → About Visual Studio Code (macOS) or Help → About (Windows, Linux). Update from code.visualstudio.com. On macOS, run VS Code from your Applications folder; a copy launched from Downloads or a disk image can be read-only.
  • The assignment folder. It contains a hidden .provenance-manifest file, which is what authorizes recording. If it is missing, recording cannot start: download or clone the starter files again.

You will need

  • A JetBrains IDE on build 261 or newer (2026.1+), such as IntelliJ, PyCharm or CLion.
  • The assignment folder, with its course-signed .provenance-manifest at the project root. Without one, the plugin stays inactive by design.

You will need

  • Neovim 0.10 or newer. Check with nvim --version (or :version inside Neovim). Update from neovim.io.
  • A Neovim plugin manager: lazy.nvim, packer.nvim, vim-plug or mini.deps.
  • The assignment folder, with its hidden .provenance-manifest file. If it is missing, recording cannot start: download the starter files again.

  1. Open the Extensions panel

    Click the Extensions icon in the sidebar (four squares), or press ⇧⌘X on macOS or Ctrl+Shift+X on Windows and Linux.

  2. Install Provenance Recorder

    Search for Provenance Recorder. On the result published by Aaryan Mehta (itsgeagle), click Install. It is free and makes no network requests while recording.

    Prefer one line? Press ⌘P or Ctrl+P, paste this, and press Enter: 

    ext install itsgeagle.provenance-recorder

    Open the Marketplace page

  3. Copy your enrollment key

    Open the command palette (⇧⌘P or Ctrl+Shift+P) and run Provenance: Show My Enrollment Key. It copies your public key. The private half is created on this computer and never leaves it.

    Enrolling lets your courses tell that the work in your recordings is yours. Do it once per computer; the credential is not tied to a course or a semester.

  4. Get your credential

    In a browser, open the /enroll page of your institution's Provenance site, for example https://provenance.your-school.edu/enroll. Sign in with your university account, paste your key, and copy the credential the page gives back.

    You do not need to be on a course roster yet; rosters usually arrive after the first submission.

  5. Import the credential

    Back in VS Code, run Provenance: Import Enrollment Token and paste it.

    If you skip enrolling, recording still works, but the log will not carry your identity and your course may not be able to attribute it to you. Do it before your first assignment.

  6. Open your assignment folder

    Choose File → Open Folder… and select the assignment folder, or any folder above it.

    Do not open a folder inside the assignment. The manifest is then outside the search and nothing starts.

  7. Check that it is recording

    Look at the status bar along the bottom of the window. If it says Provenance: recording, you are set.

    That indicator is the only visible change. A hidden .provenance/ folder appears in the assignment folder: that is the log. Do not delete or edit it. Not seeing the indicator means your work is not being logged yet. Go to troubleshooting.

  8. Submit the way your course asks

    Your course tells you which one an assignment uses.

    ZIP submission

    Open the command palette and run Provenance: Prepare Submission Bundle. A sealed .zip is saved next to your assignment folder. Upload only that .zip; it already contains your files and the log.

    Git submission

    There is no seal step. .provenance/ is part of your repository, so commit and push it with your code: 

    git add -A
git commit -m "..."
git push

    Make sure no .gitignore covers .provenance/; a missing piece shows up as a gap in your record. Push regularly: only work you have pushed is in the record.

  9. Open the plugin settings

    In your IDE, go to Settings → Plugins → Marketplace.

  10. Install Provenance Recorder

    Search for Provenance Recorder and install it. This is the signed release, which trusts only manifests signed by the real course key.

    Open the JetBrains Marketplace page

  11. Enrollment. The official JetBrains instructions do not include an enrollment step. The student guide describes enrolling for VS Code.

  12. Open your assignment as the project

    Open the assignment folder as your project, so that .provenance-manifest sits at the project root.

  13. Check that it is recording

    Look for Provenance: recording in the IDE's status bar. If it is there, you are set.

    Nothing appears? The plugin only activates for a valid, course-signed manifest at the project root. Go to troubleshooting.

  14. Prepare your submission

    When you are done, choose Tools → Provenance: Prepare Submission Bundle. A *-bundle-*.zip appears: that sealed bundle is your submission. Your course tells you how to hand it in.

  15. Add the plugin, pinned to your course's tag

    Add it to your plugin manager at the release tag your course specifies. The examples use v0.3.0. Pinning the tag is required: it ships the course's public key, and its source hash is what the analyzer recognizes as an approved build.

    lazy.nvim

    { "ProvenanceTools/provenance-neovim-recorder", version = "v0.3.0", lazy = false }

    packer.nvim

    use({ "ProvenanceTools/provenance-neovim-recorder", tag = "v0.3.0" })

    vim-plug (in init.vim)

    Plug 'ProvenanceTools/provenance-neovim-recorder', { 'tag': 'v0.3.0' }

    Do not lazy-load it. The recorder has to load every time Neovim starts so it can notice when you open an assignment folder. For packer and vim-plug, do not add opt, cmd, ft, event, { 'on': … } or { 'for': … }. If it only loads on demand, your work is not recorded even though it looks installed.

    Other plugin managers (mini.deps, built-in packages)

  16. Install, then restart Neovim

    Run :Lazy sync, :PackerSync or :PlugInstall, depending on your manager, then restart Neovim.

  17. Enrollment. The official Neovim instructions have no enrollment step, and the plugin needs no account to install.

  18. Start Neovim inside the assignment folder

    The recorder activates from Neovim's working directory, so start it inside the assignment folder: not a parent, not a subfolder. 

    cd path/to/the-assignment-folder
nvim .

    Already in Neovim? :cd path/to/the-assignment-folder works too.

  19. Check that it is recording

    Run this in Neovim:

    :lua =require('provenance.recorder.status').segment()

    If it prints ● Provenance: recording, you are set. An empty string ("") means recording is not active yet.

    A hidden .provenance/ folder also appears in the assignment folder. Do not delete, edit or commit it; the submission step bundles it for you. Not active? Go to troubleshooting.

    Add a permanent indicator to your statusline (optional)

  20. Prepare your submission

    When you have finished the assignment, run:

    :ProvenanceSeal

    A sealed .zip is written and Neovim prints its path. Upload only that .zip to Gradescope; it already includes your assignment files.

Troubleshooting

Something not working?

First the questions that apply to every editor, then the ones for yours.

Any editor

Say so early. A gap you mention is administrative; a gap found later is a conversation.

I worked for an hour and it never said it was recording.

That hour isn't in the log. Usually the cause is opening a folder inside the assignment rather than the assignment folder itself or one above it. If it was a lot of work, tell your course.

I forgot, or my laptop died, or I was offline.

Forgot entirely: mention it to your course. Laptop died or editor force-quit: nothing is lost, reopen the folder and keep going. Offline: fine, the recorder needs no network.

I deleted or edited something in .provenance/.

Tell your course and do not try to rebuild or repair it. Deleted work is gone from the record. The log is sealed, so an edit shows up as an edit however carefully it is made; reporting it makes it a non-event.

Can I see exactly what was recorded?

Yes. The session-*.slog files in .provenance/ are plain newline-delimited JSON. Open one in any text editor and read every event as it was written.

Your editor

The status bar doesn't say “Provenance: recording”.

The recorder only activates for an authorized assignment folder. Check that:

  • You opened the assignment folder itself, or a folder above it, not a folder inside it.
  • The .provenance-manifest file is still in the assignment folder.
  • You installed the build your course expects. If the manifest's signature doesn't verify against your installed build, recording won't start: reinstall the version posted for this assignment.
“Prepare Submission Bundle” isn't in the command palette.

The command only appears while the extension is active. Confirm the Provenance: recording indicator first. If your assignment uses Git submission, there is nothing to run: commit and push instead.

Sealing the submission bundle failed.

You will see an error message. The usual cause is a partially written log file, which the recorder repairs automatically on the next launch. Reopen the folder and run Prepare Submission Bundle again.

I closed my editor in the middle of the assignment.

Nothing is lost. The log is written continuously, not held until submission. Reopen the folder and keep working; the new session links to the previous one.

I lost the computer my credential was on.

If you took a backup with Back Up Student Identity Secret, restore it with Restore Student Identity Secret. If not, enroll the new machine at /enroll as in the installation steps: you get a fresh credential under the same identity. Tell your course either way, so any recording made in between can be accounted for.

I work on two computers.

That is supported. Install the recorder on the second computer, run Provenance: Show My Enrollment Key there (it makes its own key), then go to /enroll with the same university account and import the credential. Each machine gets its own credential under the same identity.

Do not copy your identity secret from one machine to the other. The backup commands exist only so you can recover a machine you lost. There is no copy on any server.

I don't see “Provenance: recording” in the status bar.

The plugin activates only on a workspace that contains a valid, course-signed .provenance-manifest at the workspace root. Without one it stays inactive by design. Check that:

  • You opened the assignment folder as the project, so the manifest is at its root.
  • The .provenance-manifest file is still there.
  • Your IDE is build 261 or newer (2026.1+).
The check prints "": recording is not active.

The recorder only activates for an authorized assignment folder. Check that:

  • You started Neovim with the assignment folder as the working directory, not a parent or subfolder. Confirm with :pwd.
  • The .provenance-manifest file is still present in that folder.
  • You installed the tag your course expects. If the manifest's signature doesn't match your installed build, recording won't start: reinstall the version posted for this assignment and restart Neovim.
:ProvenanceSeal says “not an activated assignment workspace”.

The seal command only works while recording is active. Run the check from the installation steps first; if it prints "", fix activation before sealing.

Sealing failed.

You will see an error message. The usual cause is a partially written log file, which the plugin repairs automatically on the next launch. Reopen the folder and run :ProvenanceSeal again.

I quit Neovim in the middle of the assignment.

Nothing is lost. The log is written continuously, not held until submission. Reopen the folder and keep working; the new session links to the previous one.

For instructors & TAs

Use Provenance in your course.

From choosing editors to reviewing a record.

  1. Choose the editors you accept

    There are recorders for VS Code, JetBrains and Neovim. Your course decides which of them it accepts, so tell students before they start: work written in an editor without a recorder is not recorded.

  2. Hand out the assignment folder with a signed manifest

    Recording only starts in a folder that contains a valid .provenance-manifest, signed with your course's offline key. Staff write the manifest, then sign it. In any other folder the recorder does nothing.

    How staff write and sign a manifest

  3. Decide whether enrollment is required

    Enrollment is required by default. A course can switch the prompt off in the signed manifest (policy.enrollment.required). Recording is unaffected either way, but without enrollment nothing in a submission says who produced it, so group work cannot be split between partners. That suits solo assignments and is wrong for group projects.

  4. Name the build students install

    Each released build needs its own entry on the analyzer's allowlist, or its submissions are flagged by the extension-hash check. For Neovim, give students the release tag whose hash you added.

  5. Say how work is submitted

    ZIP: students seal a .zip and upload only that. Git (VS Code): students commit and push the .provenance/ folder with their code, so make sure no .gitignore excludes it.

  6. Bring submissions into the Analyzer

    Staff ingest a Gradescope “Download Submissions” export. The roster is read from the export's submission_metadata.yml, and submissions that cannot be matched wait in the unmatched tray for you to resolve. An administrator sets up the course and semester first.

    Setting up the server (Administration)

  7. Review with a person in the loop

    • Nothing is automatic. Provenance does not email you, mark a submission or file a report; it sorts submissions for staff to look at.
    • A person reads the record, steps through what happened in order, and starts any conversation through your normal academic-integrity process.
    • Context is usually the explanation: refactors, formatters, git pull and a student pasting their own code all show up as exactly that.
    • The record cannot see thinking done away from the computer. It is a deterrent, not a cryptographic guarantee.

Administration

Run the Provenance server.

For the staff who deploy and maintain the Analyzer.

This is for course infrastructure admins, not for students or instructors. It is a summary: follow the full Admin Guide when you deploy.

Run the server Keys and manifests

Run the server

  1. Check the hosting requirements

    • Node.js: 22 LTS.
    • Postgres: 16 (10 GB disk minimum, 50 GB recommended).
    • Object storage: MinIO, AWS S3 or Cloudflare R2 (100 GB minimum, 1 TB recommended).
    • Server RAM: 512 MB minimum, 2 GB recommended.

    The server is a single Node.js process that serves both the API and the built frontend.

  2. Build it

    git clone <repo> provenance
cd provenance
npm install
npm run build

  3. Configure the environment

    Copy the example file, then fill it in:

    cp packages/server/.env.example packages/server/.env

    At minimum set PUBLIC_BASE_URL, DATABASE_URL, GOOGLE_OAUTH_CLIENT_ID, GOOGLE_OAUTH_CLIENT_SECRET, AUTH_COOKIE_SIGNING_SECRET, the OBJECT_STORAGE_* values (or BLOB_STORAGE_BACKEND=fs with its directory and signing secret) and AUTH_SUPERADMIN_EMAILS. Generate the cookie secret with: 

    openssl rand -base64 32

    AUTH_SUPERADMIN_EMAILS and AUTH_ALLOWED_HOSTED_DOMAINS are JSON arrays, not comma-separated lists. In production the server refuses to start if AUTH_SUPERADMIN_EMAILS is empty, or if the cookie secret is still the development value.

  4. Set up Google sign-in

    In Google Cloud Console, create a project and an OAuth client of type Web application. Add your site as an authorized JavaScript origin, and this as the authorized redirect URI: 

    https://provenance.example.edu/api/v1/auth/google/callback

    Use the Internal consent screen and no scopes beyond openid email profile. Set AUTH_ALLOWED_HOSTED_DOMAINS to your institution's Workspace domain.

    The hosted-domain check is the only thing keeping outsiders out. Do not loosen it.

  5. Run the database migrations

    npm run db:migrate --workspace=packages/server

    There is no --mode=migrate. This step needs the workspace's dev dependencies installed.

  6. Start the server

    node packages/server/dist/index.js --mode=api
node packages/server/dist/index.js --mode=worker

    Run the API and a worker; the worker runs the cron jobs and processes ingest. For development or a single machine, --mode=all does both. The default port is 3000 (PORT). To serve the frontend from the same server, point PUBLIC_DIR at the built packages/analyzer/dist/.

  7. Sign in and create a course

    Open your site and choose Sign in with Google. Accounts listed in AUTH_SUPERADMIN_EMAILS become superadmins on first login. Superadmins create courses at /admin/courses and semesters at /admin/courses/:courseId/semesters, then invite staff.

  8. Enable student enrollment (optional)

    Students enrol at /enroll. Until the institution signing key is set up, that page answers 503 CREDENTIAL_UNAVAILABLE and no student can onboard; recording still works. It takes the offline root key, so follow the institution key steps below.

  9. Plan retention and backups

    • Retention. After a semester is archived, a daily sweep (02:00 UTC) deletes its stored bundles once blob_retention_days has passed (default 540, minimum 30). Database rows are never deleted. Archiving is forward-only.
    • Backups. Take daily pg_dump backups of Postgres, and replicate or mirror the object storage.
    • Restore drill. Run it once before production and quarterly after, against a clean environment, never production.

Keys and manifests

How a course's assignments get their authority, and how students get an identity. Five steps, done by three different people, never all by one.

Who does what

  • Maintainer. Holds the root private key, offline. Signs course and institution certificates, and builds the recorder.
  • Course staff. Hold their course's private key and its certificate. Sign assignment manifests.
  • Deployment admin. Holds the institution key, the only private key on any server.

Nobody holds two of these in production. That is what stops a compromised server from forging an assignment, and a compromised course laptop from forging a student.

  • Assignments: the root key signs a course certificate, which authorizes the course key, which signs each .provenance-manifest.
  • Students: the root key signs an institution certificate, which authorizes the institution key, which signs student credentials.

The root key signs only those two kinds of certificate, never a manifest. The two chains meet at the root and nowhere else.

Do not run these commands on this website, and never paste or upload a private key anywhere. Each one is an npm script of the Provenance repository, run on the machine named in its step. The tools check their own work before writing anything.

  1. Create the root keypair

    Who: the maintainer. When: once, ever, on an offline machine.

    There is no separate root generator. The course-keypair generator writes a plain ed25519 keypair in exactly the shape a root key needs. Run it on an air-gapped or otherwise hardened machine, and back the private key up to physical media. 

    npm run keygen:course -- /Volumes/SECURE/root-keypair.json

    Pass only the path. Adding --course-id would mint a course certificate, which is a different artifact. The tool prints the public key, writes the private key at mode 0600, and refuses to overwrite a file or to write inside the repository.

    The root private key is the highest-value secret in the system: it authorizes every course, past and future. Never put it in the repository, never email it, never log it. The root key signs only course and institution certificates, never a manifest. Rotating it is a fleet-wide event, so plan not to.

    A development root keypair exists for local testing. It is deliberately public and must never be used for a real deployment.

  2. Create a course keypair and its certificate

    Who: course staff make the keypair; the maintainer signs the certificate. When: when a course is onboarded, then each new certificate window.

    Course staff: generate the keypair, on a secured machine

    npm run keygen:course -- /Volumes/SECURE/cs61a-fa26.json

    The public key is printed. The private key is written to the path you chose at mode 0600: back it up to physical media. Send the maintainer only the public half.

    Maintainer: sign the certificate, with the root keypair

    npm run mint:course-cert -- \
  --course-id berkeley-cs61a --course-pubkey <64-hex-from-generate-step> \
  --valid-from 2026-08-20 --valid-until 2027-01-15 \
  --root-keypair /Volumes/SECURE/root-keypair.json \
  --out /Volumes/SECURE/cs61a-fa26.cert.json

    When one machine holds both keys, keygen:course can do both steps in one run: pass --course-id, --valid-from and --valid-until (and optionally --root-keypair and --cert-out) along with the output path.

    Keep the validity window short, one semester. An offline recorder cannot learn that a key was revoked, so a short window is the only protection. The certificate is checked against the root public key before it is written.

  3. Create the institution key and its certificate

    Who: the deployment admin on the server; the maintainer on the offline machine. When: once per deployment, and only if students enrol at /enroll.

    There is one institution key per deployment, not one per course. Without it, /enroll answers 503 CREDENTIAL_UNAVAILABLE (no_institution_key) permanently and no student can be onboarded. Recording itself still works.

    Admin, on the server: generate the keypair

    npm run keygen:course -- /secure/institution-keypair.json

    Positional path only. Carry just the public key to the maintainer's offline machine.

    Maintainer, on the offline root machine: sign it

    npm run mint:institution-cert -- \
  --institution-id berkeley --institution-pubkey <64-hex-from-generate-step> \
  --valid-from 2026-08-20 --valid-until 2027-08-19 \
  --root-keypair /Volumes/SECURE/root-keypair.json \
  --out /Volumes/SECURE/berkeley-institution.cert.json

    Admin: bring the certificate back and set both halves in one variable, then restart the API 

    PROVENANCE_INSTITUTION_KEY='{"private_key_hex":"<64 hex>","cert":<the cert JSON>}'

    The institution private key never leaves the server, and the root private key never touches it. Treat the variable like the OAuth client secret, or more carefully: whoever holds it can forge student attribution until the certificate's window closes. Keep the window short: there is no offline revocation.

    It is deliberately not stored in Postgres, so a restore from backup will not bring it back. Keep it in your deployment's secret handling and in the restore runbook. If it leaks, sign a fresh certificate for a new keypair with the offline root key, replace the variable and restart. Certificates already issued stay valid, because recorded bundles must keep verifying.

    Watch the end of each window: when the certificate lapses, /enroll answers 503 with cert_out_of_window, which students see as “we cannot issue credentials right now”.

  4. Write and sign an assignment manifest

    Who: course staff. When: for every assignment, before it is handed out.

    Put the unsigned .provenance-manifest at the root of the assignment starter folder, the folder students will open: 

    {
  "assignment_id": "hw03",
  "semester": "fa26",
  "issued_at": "2026-09-15T00:00:00Z",
  "files_under_review": ["hw03.py"],
  "course_id": "berkeley-cs61a",
  "collaboration": "solo",
  "submission": "bundle",
  "scope": "directory",
  "policy": {
    "capture": {
      "selection_change": true,
      "focus_change": true,
      "terminal": true,
      "heartbeat_interval_ms": 30000
    },
    "enrollment": { "required": true }
  }
}
    • assignment_id is unique per assignment. Changing it each time is what stops an old session being replayed against a new assignment.
    • files_under_review lists workspace-relative paths. Only these get the expected-content check that detects outside changes; other files are still recorded.
    • course_id must equal the course_id in the certificate you sign with.
    • collaboration is solo or group; submission is bundle or git; scope is directory or repo.
    • policy.capture lets a course turn capture down. A student cannot turn it off, because it sits inside the signed payload. Leave out keys to keep the default (everything on, 30 s heartbeat).
    • policy.enrollment.required defaults to true. Setting it to false stops the enrollment prompt but loses attribution: nothing in a submission says who produced it, so group work cannot be split between partners. It only takes effect at manifest format 2.0.

    Sign it, from the course's secured machine

    PROVENANCE_COURSE_KEYPAIR_PATH=/Volumes/SECURE/cs61a-fa26.json \
PROVENANCE_COURSE_CERT_PATH=/Volumes/SECURE/cs61a-fa26.cert.json \
  npm run sign:manifest -- /path/to/assignment-starter/.provenance-manifest

    Leave out sig and course_cert: the signer adds both, and replaces them if you re-sign. It checks the whole trust chain before writing, and refuses to write a manifest that would not verify, for example when course_id differs from the certificate's. Add --format 1.0 only for the legacy shape, which is still supported for archived work.

  5. Build the recorder and update the extension hashes

    Who: the maintainer. When: once per root-key rotation, not once per course, then again for each recorder release.

    One VS Code build serves every course: it embeds only the root public key, and a course's authority travels in its certificate. 

    PROVENANCE_ROOT_PUBLIC_KEY_HEX=<the maintainer's root public key> \
  npm run build:prod --workspace packages/recorder

    The script refuses to run if the key is missing, malformed, or the development key, so a misconfigured release cannot quietly ship a development build. It restores the source afterwards.

    Only while version 1.x manifests are still in the field, also pass the old course key 

    PROVENANCE_ROOT_PUBLIC_KEY_HEX=<the maintainer's root public key> \
PROVENANCE_LEGACY_COURSE_PUBLIC_KEY_HEX=<the old course public key> \
  npm run build:prod --workspace packages/recorder

    Then add the new build to the analyzer's list of known-good hashes 

    npm run update-hashes -- --root-keypair /Volumes/SECURE/root-keypair.json

    Without this, submissions from the new build are flagged extension_hash_mismatch. Embedding the legacy key changes the built files and so the hash: to allow both a 1.x-compatible and a 2.0-only build, run it once with the legacy variable set and once without. Other modes are --show, --no-build, --hash <hex>, --remove <hex>, --clear and --help.

    The JetBrains and Neovim recorders build in their own repositories. Compute their hashes there, then add each with --hash <hex>:

    JetBrains

    ./gradlew :recorder:computeExtensionHash

    Neovim, inside Neovim

    :lua print(require('provenance.recorder.commands.extension_hash').compute_installed())

    Where the root public key goes

    • PROVENANCE_ROOT_PUBLIC_KEY_HEX on the server, at runtime. Unset is allowed, but 2.0 submissions then validate as warn with check 2 skipped.
    • VITE_ROOT_PUBLIC_KEY_HEX when building the analyzer, for the standalone /local route.

    Both are build-time or deploy-time values: rotating the root key means rebuilding and redeploying the analyzer and all three recorders.

If something fails

“HOSTED_DOMAIN_MISMATCH” when signing in.

The account's domain doesn't match AUTH_ALLOWED_HOSTED_DOMAINS. Check the variable, and that the person is using their institutional account rather than a personal Gmail.

The worker isn't processing jobs.
  • Confirm the worker is running (--mode=worker or --mode=all).
  • Look for failed jobs in the pgboss.job table.
  • Check the server logs for pg-boss error entries.
  • Make sure the API and the worker use the same DATABASE_URL.
The retention sweep isn't running.

Check pgboss.schedule for retention_sweep. If it is missing, restart the worker: it registers the schedule on startup.

MinIO connection refused.

Confirm MinIO is running and reachable from the server host, using its /minio/health/live endpoint.

Manifest signing refuses to write.

The manifest's course_id does not match the certificate's, so the chain check failed. Fix the manifest or use the right certificate.

A new recorder build shows extension_hash_mismatch.

npm run update-hashes has not been run for that build. Run it once per build variant.

Every 2.0 submission validates as warn, check 2 skipped.

PROVENANCE_ROOT_PUBLIC_KEY_HEX is not set on the server. If a whole cohort lands on warn, check this first.

Students cannot enrol: “we cannot issue credentials right now”.

/enroll is answering 503 CREDENTIAL_UNAVAILABLE. The reason is no_institution_key (the variable is not set) or cert_out_of_window (the institution certificate has lapsed: sign a new one).

A database migration fails.

“relation already exists” means a migration was partially applied: look at drizzle.__drizzle_migrations.

Dropping and recreating the database is for clean development environments only. Never do it in production: diagnose the failed migration and apply the missing DDL manually.
